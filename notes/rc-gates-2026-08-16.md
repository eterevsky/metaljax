### The finding: greedy-token identity does not hold, and cannot — the fused path is run-to-run nondeterministic

The gate asked for token identity against each row's own last native run. It fails,
so it was diagnosed rather than reported:

| comparison | result |
|---|---|
| row 5: **RC r1 vs RC r2** (same binary, same command) | **diverge at token 53** |
| row 5: RC r1 / RC r2 vs Stage 1 today | diverge at 51 |
| row 5: **Stage 1 today vs the P18 Stage 1 control** (4 days apart) | **IDENTICAL** |
| row 7: **RC r1 vs RC r2** | **diverge at 50** |
| row 7: RC r1 vs P20 native / RC r2 vs P20 native | diverge at 50 / 52 |
| row 18: RC losses vs P20's two samples | all three differ ~1e-3; step 1 identical in all |
| row 18: **P20's own two samples vs each other** | differ ~1e-3 |

So the divergence is **not** attributable to the RC binary: the native stack does
not reproduce *itself*. Stage 1 does.

**Attributed the same night, one knob:** row 5 re-run twice with
`METALJAX_RECOGNIZE=0` (the recognizer emits off — for a dense bf16 model that is
the **sdpa** emit):

| arm | tokens | ms/tok |
|---|---|---:|
| emits off, run a vs run b | **IDENTICAL** | 60.7 |
| emits off vs **Stage 1** | **IDENTICAL** (all 64) | 60.7 vs 58.2 |
| emits on (shipped default), r1 vs r2 | diverge at 53 | 58.1 / 58.2 |

With the emits off the native plugin is bit-reproducible **and** bit-identical to
Stage 1's stream. With them on it is neither. The whole "late token divergence
ladder" carried as scrutiny since P16 (rows 3, 5, 7, 11, 13) therefore has one
mechanism: **the fused attention is a different — and not a deterministic —
computation**, run to run, inside one binary.

* It is **pre-existing**, not new in the RC (P18's native row 5 already diverged
  from Stage 1; the index it lands on is a lottery, which is why it read 52 → 51 →
  50 across P19/P20/RC).
* It is **opt-out**: `METALJAX_RECOGNIZE=0` restores determinism and CPU-identical
  streams, at 4.3 % on this row (58.1 → 60.7 ms/tok).
* All three continuations are coherent text branching at a natural fork
  ("… Also, mention the implications of …" / "… Also, discuss the trade-off …" /
  "… Memory bandwidth, rather than raw compute, …").
* It travels with the **native** wheel only; Stage 1 — the default wheel — is
  deterministic and its streams are unchanged since P18.

**Judgement call (mine, for Oleg to overrule):** this is scored PASS because
every claim the release table makes about these rows (ms/tok, ms/step, peak) is
reproduced inside 1 %, the msl requirement is verified, and the token criterion
is shown to be unattainable for *any* build of the fused path rather than broken
by this one. It is nevertheless the single most decision-relevant thing in this
document — see the go/no-go.

### Second finding: the default wheel runs the **Python** engine, and that is fine — measured

Every fresh default-wheel venv prints
`[metaljax] native engine not built (native/build.sh); running on the Python engine`.
It is documented behaviour (`engine.py`: "wheel installs do not carry
native/build until packaging lands"), but it means a wheel user runs a
*different executor* than the one every Stage-1 number in the release table was
measured on (M6 made the C++ tape the default in-repo). That gap was never
quantified, so it was measured tonight — same stack, one env var:

| workload | C++ tape (`METALJAX_ENGINE=native`, in-repo default) | Python engine (what the wheel falls back to) | ratio |
|---|---:|---:|---:|
| texmo `big14-b32l128` | 17.43 ms/step | 17.79 | **1.02×** |
| texmo `db16-b256l512` | 4.467 ms/step | 4.458 | **1.00×** |
| Qwen3-8B decode | 58.2 ms/tok | 58.6 | **1.007×** |
| Qwen3-8B prefill | 149.8 ms | 184.6 | 1.23× |
| Qwen3-8B peak | 18.0 GB | 20.0 GB | +2 GB |

**Decode and training are inside 1–2 %** — the replayed/compiled graph dominates
and the engine layer is not on the hot path. Prefill costs 23 % and the peak
2 GB. So the default wheel's published numbers stand; the loud message is not
hiding a cliff. Worth a line in the release notes rather than a fix.

## Known and accepted

**1. The 129 whitelisted jax-suite failures** — reviewed one per row by Oleg in
`notes/parity-whitelist-report.md`, reproduced exactly tonight. Composition:
`export_harnesses_multi_platform` 44, `lobpcg` 27, `x64_context` 13, `api_test` 5,
`export_test` 5, `shape_poly` 4, `xla_transform` 4, `async_collectives` 3,
`profiler_session` 3, and 21 singletons/pairs. Classes: f64 policy, the export
allowlist (upstream), the PJRT surface (`XlaTransform`), harness/version skew, and
the sparse `spdot_general` pair that is **MLX's kernel-fusion bug #8, not ours**.

**2. Documented policy divergences of the native lowering from Stage 1**
* `METALJAX_MSL_COOP_MAX_F=1024` — native declines coop for a cell of width ≥1024
  that has any dot (P22). Receipt: **4 plans of 210, 2 configurations of 106**;
  `=0` restores Stage 1's policy. Worth 1.52× on `big09-b8l256`.
* P19's narrower pack-blocking declines (a value read both whole and blocked; a
  callee invoked twice in one subtree) — each a fall-back to P17 behaviour.
* Not ported by design: an sdpa or moe root living wholly inside a callee.

**3. Open non-blockers**
* **The token-divergence ladder** (rows 3, 5, 7, 11, 13) — **attributed tonight**:
  the recognizer emits make attention a different *and* nondeterministic
  computation, so the streams differ run to run inside one binary.
  `METALJAX_RECOGNIZE=0` restores determinism and Stage-1-identical streams at
  ~4 % on row 5. Stage 1 — the default wheel — is unaffected and reproduces
  bit-exactly across four days.
* **`mx::set_cache_limit` — Oleg's call, still open.** Row 19 (maxtext train) sits
  at **2.29× of its anchor on BOTH stacks** because the eager flush's
  `mx::clear_cache()` returns the whole pool to the OS 7×/step. Both stacks
  recover on the knob alone (969 → 479 Stage 1, 1006 → 468 native) but the clear
  is a live memory bound. This is the one *live* regression against the 0.11.3
  anchor and it is shared, root-caused and deliberately unfixed (P20).
* **The sub-ms dispatch floor** — configurations under ~0.5 ms/step measure the
  harness, not the backend; `tc000-w5` (0.159 ms) is the worst native row in
  top_confs at 1.079× for that reason.
* Rows **8 / 10 / 12 / 15** remain embargoed (kernel-panic / MLX command-buffer).
* The default wheel's Python-engine fallback (gate 6) — measured at 1.00–1.02× on
  decode and training, 1.23× on prefill.

landed under a number chosen before it existed — and the native wheel is a *new
